# 요구사항 — 맨 위 표가 합격 기준의 원본
<!-- 표는 5칸만: REQ | P | 합격 기준 한 줄(30자 안팎, 값·조건까지) | D | 확인 방법. 검사 명령·증거는 아래 "상세"에 글머리표로. 같은 REQ를 표에 두 번 쓰지 않는다. -->
<!-- REQ는 8개 이하. 데이터 흐름 칸(읽기·표기 맞추기·거르기·꼬리표·순서·보여 주기)이나 규정 조문 단위로 묶는다. 요청자 답 하나하나는 REQ가 아니라 상세의 세부 줄. 🟡·P1은 decisions에 한 줄. -->
<!-- 합격 기준은 테스트로 옮길 수 있게 숫자·조건으로 쓴다("넉넉하게" ✗ → "준비량 ≥ 예측 × 1.15" ○). 확인 방법: 테스트 이름 / 체크리스트(문서·화면) / 담당자 Q-ID(수용). -->

## 한눈에
| REQ | P | 합격 기준 (한 줄) | D | 확인 방법 |
|---|---|---|---|---|
| REQ-001 | P0 | 합의 후 작성 | | |

P0: 완주 필수 / P1: 유용 / P2: 여유가 있을 때.

## 상세 — REQ마다 검사 명령·상태·증거
- REQ-001 — 검사: `미정` / 상태: TODO / 증거:

## 규칙
- checks.json에 같은 ID·우선순위·검증 명령(argv 배열)을 등록한다. regression 배열에 기존 동작 검증을 최소 1개 넣는다.
- 증거: artifacts/eval_*.json의 해당 REQ, exit code, source_stable.
- skeleton.md·결정표는 REQ-ID를 참조한다. AI가 테스트 통과용으로 기준을 약화하지 않는다.
- 정책 변경·기준 오류는 사람 확인→새 D-ID·대체 관계→관련 REQ/checks/테스트/handoff 갱신 순서로 반영한다.
- 지정 src/ 프로젝트는 해당 프로젝트 검증 명령·실제 로그를 기록한다.

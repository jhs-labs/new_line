# 로컬 데이터 작업 규칙

## 파일·설정 규칙 (가장 먼저 지킨다)
- **파일 목록 고정**: fde/work에는 템플릿 파일(problem·data_map·analysis·interview·stakeholders·decisions·requirements·rules·skeleton·state·handoff), 키트가 만든 checks.json·session.json, `fde/work/analysis/` 폴더의 분석 스크립트만 둔다. 루트에는 src·tests·config.json과 README가 요구한 제출물만 둔다. 그 밖의 새 파일이 필요하면 만들기 전에 파일명과 이유를 말하고 사람의 허락을 받는다.
- **분석 결과**: 분석할 때마다 새 파일을 만들지 않는다. `fde/work/analysis.md` 끝에 한 건 10줄 이내(질문·명령·표 5줄 이내·결론·영향 D)로 덧붙이고, 채팅에는 결론 한 줄만 말한다. 원본 결과 JSON·추적 파일은 저장하지 않는다(필요하면 명령을 다시 실행한다).
- **검증 결과**: validation·review 같은 별도 문서를 만들지 않는다. state.md에 `명령 / exit code / 통과 수` 한 줄로 남긴다.
- **문서 크기**: 파일 하나는 200줄 이내로 쓴다. 넘으면 맨 위 5줄 요약을 두고 오래된 내용은 줄이거나 근거 절로 보낸다.
- **단계 전환 정리**: STATE를 넘길 때 `git status --short`로 새로 생긴 파일 목록을 보여 주고, 위 목록 밖의 파일은 지우거나 합칠지 사람에게 묻는다.
- **합의값 = 설정 + 기본값**: 담당자가 정한 숫자·기준은 루트 `config.json`에 `"키": 값, "_키": "Dn 근거 한 줄"` 형식으로 넣고, 코드는 이 파일만 읽는다. 같은 값을 코드에 다시 쓰지 않는다. API·화면의 파라미터 기본값도 이 값이다. 파라미터 없이 불러도 합의값으로 결과가 나와야 한다.
- **템플릿 칸 유지**: 템플릿의 `이름:` 칸(예: problem의 `성공 기준:`·`만들 것:`·`만들지 않을 것:`·`제약:`·`Unknown:`)은 지우거나 제목·문단으로 바꾸지 않는다. 내용은 칸 뒤에 쓴다.
- **테스트 먼저**: 정책이 걸린 REQ를 구현하기 전에 그 REQ의 테스트를 먼저 쓰고 실패 출력을 보여 준다. 사람이 "구현해"라고 하면 그때 구현한다.
- **멈출 조건**: decisions에 없는 규칙·숫자가 필요하면 임의로 정하지 말고 멈추고 질문 초안(또는 숫자가 든 결정문 초안)만 준다.
- **커밋 단위**: REQ 하나가 통과할 때마다 `REQ-xxx: 요약 (Dn)`으로 커밋을 제안한다. 단계 전환 때도 커밋한다.
- **확인 방법**: REQ마다 확인 방법을 정한다. 숫자·조건이 있으면 테스트, 문서·화면이면 체크리스트와 직접 확인 기록, 담당자 수용이면 답 원문 Q-ID. 테스트로 못 옮길 만큼 막연한 합격 기준이면 숫자·조건으로 고칠 안을 사람에게 먼저 묻는다.
- **D ↔ 코드 대조**: 단계를 넘길 때 decisions의 D마다 실제 위치(config 키·파일:함수·커밋)를 확인한다. 코드·설정에 없는 D, 문서와 값이 다른 D만 목록으로 보고한다. 문서에 적힌 결정은 코드·커밋과 연결돼야 한다.
- **안 묻고 정한 것 보고**: 단계를 넘길 때 이번 단계에서 사람에게 묻지 않고 정한 것(기본값·빈 값 처리·경계·제외 등)을 목록과 근거로 보고하고, decisions에 🟡로 남길지 묻는다.
- **REVIEW 약점 형식**: REVIEW의 "틀릴 수 있는 경우"는 3개 이상, 각각 ① 약점 지점(파일:줄·함수·데이터·경계값) ② 왜 위험한지·어디까지 번지는지 ③ 다음에 검증·개선할 것, 세 줄로 쓴다. 지점은 실제 코드에서 검색해 확인한 위치만 쓴다.

## 그 밖의 작업 규칙
- 첫 응답에서 현재 작업 폴더·Git 루트를 확인한다. 프로젝트 폴더가 아니거나 Git 루트가 없으면 멈추고 알린다.
- 담당자 답을 받으면 같은 응답 안에서 interview Q-ID에 원문을, decisions.md에 D-ID(결정·영향 REQ·설정 키)를 추가한다. 기록 전에는 그 정책을 구현하지 않는다.
- 담당자 질문 초안을 만들기 전에 decisions.md를 확인한다. 이미 있는 결정은 다시 묻지 않고 D-ID를 인용한다.
- Computer Use·브라우저 자동화·화면 캡처를 쓰지 않는다. 화면 확인은 HTTP 응답과 테스트로만 한다.
- Codex·npm 전역 패키지를 업데이트·설치하지 않는다(`npm install -g`, `sudo` 설치 금지). 필요한 의존성은 표준 라이브러리로 대체하거나 사람 승인 후 프로젝트 안에만 둔다.
- `git add -A` 전에 `git status --short`로 `.codex/`·`.config/`·셸 설정 같은 홈 숨김 파일이 없는지 확인한다. 보이면 commit하지 말고 .gitignore부터 고친다.
- 웹 서버는 프로젝트 README가 정한 포트를 쓴다. 정하지 않았으면 0.0.0.0:3000(흔한 개발 서버 포트)에 띄우고 `--port`로 바꿀 수 있게 한다. 띄운 뒤 그 포트로 HTTP 응답을 확인한다.
- 서버 시각은 UTC일 수 있다. 판정 기준 시각에 `now()`를 쓰지 않고 합의한 D(데이터 마지막 시각 등)를 쓰며, 기록의 시각에는 시간대를 붙인다.
- 과정 기록(problem·interview·decisions·requirements·skeleton·state·handoff)은 fde/work에만 둔다. docs/ 등에 같은 종류의 기록을 따로 만들지 않고, 프로젝트가 지정한 전달 문서는 fde/work를 근거로 쓴다.
- D-ID는 `D1, D2…` 형식으로 쓴다. 정책이 걸린 구현 요청에 D-ID가 없으면 적용할 D를 먼저 확인하고, 해당 D가 없으면 구현하지 말고 질문 후보로 돌린다.
- REQ 검사가 통과하면 같은 응답에서 `git add <파일>`과 `REQ-xxx: METHOD ④ 요약 (Dn)` commit 명령을 제안하고 state의 마지막 commit을 갱신한다. Git 신원·전역 설정은 바꾸지 않는다.
- 체크포인트(45·80·115·140·155·170분)마다 `python fde/kit/status.py --intent` 결과와 fde/docs/SELFCHECK.md의 해당 체크리스트로 빈칸을 보고한다.
- 건수·순위·등급·테스트 수 같은 숫자는 방금 실행한 명령 출력에서 옮긴다. 기억·암산으로 쓰지 않고, 실행하지 않았으면 미실행이라고 쓴다.
- 문서에 쓰는 규칙·결정·결과에는 근거(파일:함수, Dn, Q-ID, 명령)를 붙인다. 붙일 수 없으면 `(추정)` 또는 Unknown으로 쓴다.
- 사람이 읽을 문서는 맨 위에 3줄 요약을 두고, 표는 4칸 이하·칸 안은 짧은 말만 쓴다. 긴 설명은 글머리표로, 명령·출력 원문은 맨 아래 근거 절에 둔다. 데이터 지도는 fde/work/data_map.md 틀을 쓴다.
- decisions는 맨 위 "한눈에"(주제별 한 줄, ✅🟡❓ 기호)를, requirements는 맨 위 5칸 표(REQ | P | 합격 기준 한 줄 | D | 확인 방법)를 먼저 갱신한다. 한 줄은 사람이 바로 이해할 말로 값까지 쓰고, 단서 문장을 덧붙이지 말고 상태 기호로 표시한다. 사용자가 결정 문장을 직접 주면 그대로 쓴다.
- 담당자에게 보낼 메시지 초안은 채팅에 그대로 붙일 평문으로 쓴다. 표·굵게·코드블록 없이 한 줄에 한 항목, 5줄 이내.
- 서버를 띄워 확인했으면 같은 응답에서 끄고 포트가 비었는지 확인한다. 서버를 켜 둔 채 응답을 끝내지 않는다.
- 문서에 함수·설정 키·규칙 이름을 쓰기 전에 src에서 검색해 실제로 있는지 확인한다. 처음 쓰는 모듈·함수는 import·실행으로 존재를 확인한다.
- 결정을 새 D로 대체하면 옛 결정의 핵심 표현을 저장소 전체에서 검색해 남은 문장을 고치거나 "대체됨→Dn"으로 표시한다.
- 완료·통과 주장은 명령·exit code·핵심 출력과 함께 쓴다. "통과했습니다"만 쓰지 않는다.
- 프로젝트 README의 지정 구조·실행·데이터 사용·전달 정책이 우선한다. 기존 src와 사용자 변경을 보존한다.
- 시작/재개는 README와 fde/work의 problem/requirements/state/handoff부터 읽는다. 없으면 필요한 템플릿만 만든다.
- 새 세션의 첫 응답은 handoff 맨 위 요약 칸만 읽고 "STATE / 다음 3행동 / 이 세션이 맡을 범위"를 한 줄씩 되말한다. 기록 담당 세션이면 그 요지를 handoff의 `이어받기 확인:` 칸에 시각과 함께 남긴다.
- handoff 맨 위 요약 칸(목표·STATE·실행·핵심 결정·다음 3행동·이어받기 확인)은 `이름: 내용` 형식으로 20줄 안에 유지한다. 제목·문단으로 다시 쓰지 않고, 이력은 요약 아래나 git log로 보낸다.
- 80분·140분 체크포인트에서 handoff 요약을 갱신하고 새 세션으로 넘어가기를 사람에게 제안한다. Compact만 반복하며 한 세션을 끝까지 끌지 않는다.
- 마무리 무렵 git log·decisions·REVIEW로 나중에 받을 만한 질문 5~6개를 만든다. 설명 틀은 두 가지다: "왜 이렇게 했나"는 결론→근거(Dn)→안 했으면 생기는 일, "장애·틀릴 때"는 약점 지점(파일·함수·데이터·경계)→왜 위험·어디까지 번지나→다음에 검증·개선할 것. 사람이 직접 답하게 하고 AI는 빠진 칸만 지적한다.
- 여러 세션을 동시에 쓸 때 기록 파일(interview·decisions·requirements·state·handoff)을 고치는 세션은 사람이 지정한 1개뿐이다. 다른 세션은 맡은 코드·검토만 하고, 새 결정·질문은 "D 후보"로 보고만 한다. 같은 파일을 두 세션이 동시에 고치지 않는다.
- 필요할 때 fde/docs/METHOD.md와 STAGE_PROMPTS.md의 현재 STATE만 읽는다. 전부 순차 실행하거나 서류 자체를 목표로 삼지 않는다.
- 실제 사례·현재 처리·성공 기준부터 묻고 결과를 바꿀 핵심 질문 3~5개를 고른다. 받은 답 원문·출처는 interview Q-ID, 결정은 decisions D-ID에 참조한다.
- 예시·README의 업무 가정을 실제 정책으로 단정하지 않는다. 핵심 미확정은 질문하고, 범위·합격 기준의 실제 사람 승인 전 본 구현하지 않는다.
- requirements가 합격 문장의 원본이다. 독립 work 후보만 checks.json과 ID·우선순위·검사 명령을 맞춘다. 기존 src 프로젝트는 자체 검사·구조로 전달한다.
- skeleton에 읽기→정규화→정제→판정→순위/집계→표시의 입력·출력·정책 위치를 연결한다. 7 STATE와 6 METHOD는 별개이며 여섯 파일을 강제하지 않는다.
- 원본/표준 값을 추적하고, 같은 파일의 배타적 정상/격리/중복만 더한다. 경고를 재집계하지 않고 실제 반복·등급 미상을 임의 제거하지 않는다.
- 작은 실제 입력→출력을 먼저 확인하고 해당 REQ의 반례·경계·회귀를 검사한다. 판정·계산은 결정론적 코드로 수행한다.
- 관련 검사를 준비하고 실제 통과/실패·timeout·exit code·소스 일치를 남긴다. 테스트 통과를 고객 수용으로 기록하지 않는다.
- 사람의 실행 전 예상·직접 코드 추적·내 말 설명을 AI가 대필한 과거 행동으로 만들지 않는다. AI 초안은 사람이 대조한다.
- 정책 변경은 새 D-ID·대체 관계·영향 REQ·검사·handoff로 연결한다. 미확인 값을 구현 완료로 만들지 않는다.
- 기본 수정 범위를 좁히되 API/공통 검사 연결 수정은 이유·영향을 설명하고 확인된 범위에서 최소 변경한다.
- 같은 실패 3회면 반복 수정을 멈추고 원인·작은 재현·대안 2개를 보고한다. 새 의존성·외부 전송은 프로젝트의 승인 규칙을 따른다.
- champion은 promote.py로만 갱신하며 실패하면 기존 정상본을 보존한다. bundle은 work 밖의 파일을 자동 포함하지 않는다.
- 실제 전달 위치에서 새 프로세스로 실행하고 서버 준비/HTTP 응답과 유한 명령의 exit code를 구분한다.
- 3시간 세션 예산은 참고값이다. 실제 마감과 필수 기능·정확성·큰 위험·최종 전달 시간을 보호하고 선택 기능·장식을 먼저 줄인다.
- STATE/GATE는 실제 근거로 기록한다. 내부 빈칸·Git 상태 때문에 전달을 지연하지 않고 실패·답 없음·미실행을 숨기지 않는다.
- 변경은 한 세션에서 한다. 가능한 읽기 전용 교차 검토를 하고 길어진 작업은 handoff의 목표·근거·다음 3행동으로 재개한다.
- 비밀·개인정보·원본 데이터·작업 로그를 공개하지 않는다. 허용된 자원·자동화·네트워크만 사용하고 해당 환경의 정책을 우회하지 않는다.

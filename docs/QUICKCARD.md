# QUICKCARD — 현재 단계만 보기

**묻기 → 정하기 → 준비 → 한 번 실행 → 검사 → 사용자 확인 → 전달.**

## 시작 0~5분 — 이 순서로

0. 키트는 프로젝트 폴더 **밖**에 받는다: `git clone <키트 주소> /tmp/new_line`. 프로젝트 폴더 안에 받으면 전달물·commit·Codex 검색에 섞인다.
   `pwd; ls -a; date` — 프로젝트 폴더가 홈(`.bashrc`·`.config`가 보임)인지, 서버 시각이 UTC인지 확인한다.
1. **한 번에:** `python3 /tmp/new_line/install.py --target . --start`
   .gitignore(`.codex/` 로그인 정보·셸 설정 제외) → `git init`(없을 때만) → `init: 프로젝트 원본` commit → 키트 설치 → work 양식 → `chore: new_line 설치` commit.
   - 상위 폴더가 이미 Git이면 멈춘다. 프로젝트 폴더를 다시 확인한다.
   - 모르는 숨김 파일이 보이면 commit 전에 멈춘다. 비밀이면 .gitignore에 넣고, 프로젝트 파일이면 `--allow-hidden`.
   - 이미 commit이 있으면 원본 commit은 건너뛰고 키트 파일만 commit한다.
   - 단계별로 하려면 [GIT](GIT.md)의 `--gitignore-only` → init commit → install 순서.
2. Codex 업데이트 안내가 뜨면 건너뛴다. `npm install -g`·`sudo` 설치를 하지 않는다.
3. **프로젝트 폴더에서** Codex를 연다. 상위 폴더에서 열면 AGENTS.md가 로드되지 않는다.
4. "지금 적용 중인 AGENTS.md 규칙 3개만 말해 줘"로 로드를 확인한다. 못 말하면 다시 연다.
5. state.md에 작업 폴더·Git 루트·AGENTS 로드 확인을 적는다.
6. 사전 점검·시작 때 Codex 모델과 effort(가능한 최고값)를 확인한다.
7. 포트: README에 정해져 있으면 그 포트, 없으면 **3000**(흔한 개발 서버 포트). 서버는 0.0.0.0에 띄우고 미리보기로 화면이 보이는지 바로 확인한다.


## 처음 50분 흐름 — CONTRACT 끝까지

[담당자] = 담당자 창, [Codex] = Codex 창. ○는 데이터에서 센 값으로 채운다.

**0~5분 · 설치 + 숨은 요구 3개 (데이터 보기 전)**
- [Codex] `지금 적용 중인 AGENTS.md 규칙 3개만 말해.`
- [담당자] 아래 질문 카드 1·2·3번을 그대로 던진다.
- 질문 한도가 넉넉하면 하나 더: "지금 이 판단은 누가, 얼마나 걸려서, 얼마나 자주 하나요?" → 나중에 "왜 필요한가·일이 늘지 않나"에 답할 숫자.

**5~20분 · 데이터 읽기 (Codex는 읽기만)**
```
코드 짜지 마. README와 data/를 읽고 파일마다 표로: 행 수 | 단위·기준 | 상태값 종류 | 빈칸·이상값 | 계산에 쓰는 열.
README에 이미 답이 있는 것(방향·단위·세금)은 따로 표시해.
내 예상: [단위 변환이 필요한 열], [빼야 할 상태값]이 있다.
```
```
담당자 답 원문: [붙여넣기]. interview에 원문, decisions에 ✅·🟡로 기록.
담당자 질문 초안 5개. 조건: data/·README로 답이 안 되는 것만 / 데이터에 없는 개념 넣지 마 / 전부 숫자가 든 "○○로 할게요, 맞죠?" 모양.
```
→ **보내기 전 10초:** 데이터에 있나? 처음 듣는 단어 있나? 숫자 있나?

**질문 전에 막 돌려 보고 "어? 이상한데"를 AI가 숫자로 검증하게 한다.** 사실 확인 질문은 데이터를 봐야 생긴다. 질문 수에 한도가 있으면 1·2·3번 말고는 이 점검 뒤에 쓴다.
```
코드 고치지 마. 먼저 막 집계: 파일을 공통 키로 잇고, 주요 열(장비·날짜·종류 등)별 건수와 비율, 상위 10개를 표로. 정교할 필요 없다.
그다음 아래 12개를 하나씩 숫자로 확인해서 표로 줘: 항목 | 발견 여부 | 근거 숫자(행 수·비율·예시 3행) | 데이터로 확정 / 담당자 확인 필요 | 확인 필요면 질문 한 줄.
추측으로 채우지 마. 못 확인하면 "확인 못 함".
1 키 조인: 파일끼리 몇 % 붙나, 안 붙는 행의 형식(접두사·대소문자·공백·자릿수)이 날짜·출처별로 다른가. 이름으로 잇는다면 표기 변형(약칭·법인 표기·영문명·상하위 조직)이 몇 개로 갈라지나
2 단위·스케일: 같은 항목이 출처·기간별로 10배·1000배 차이 나나, 단위 표기와 실제 값 크기가 맞나
3 부호·방향: 출처별로 평균 부호가 반대인가, 위치·구역별로 방향성이 있나
4 빈칸·특수값: 빈칸·-999·0이 어느 열에 몇 개, 특정 출처·기간에 몰리나
5 중복·반복: 같은 키 중복 행, 재측정·재처리 회차 — 어느 회차를 써야 하나
6 시간: 형식이 섞였나, 시간대, 원인 시각과 결과 시각의 순서가 말이 되나
7 표본: 묶음별 표본 수, 측정 점 수가 다른 행, 1~2개짜리 묶음
8 건수 vs 비율: 건수 상위와 비율 상위가 다른가 (처리량 차이)
9 섞임: 나쁜 묶음의 구성(종류·앞 단계·배정)이 다른 묶음과 다른가, 상위 N개가 같은 개체 하나로 도배됐나
10 기준 차이: 종류별로 원래 수준이 다른가, 테스트·실험 행이 섞였나
11 이벤트 시점: 결과가 바뀐 날 전후에 이벤트(교체·점검·업데이트)가 여러 개 겹치나, 어느 쪽이 데이터와 더 맞나
12 사람이 쓴 문서: 보고서·메모의 숫자와 주장을 데이터로 다시 계산하면 맞나
마지막에 "담당자 확인 필요"만 우선순위대로 "○○로 할게요, 맞죠?" 질문으로 모아.
```
→ 데이터로 확정되는 건 직접 정하고(🟡), **담당자만 아는 것만 묻는다.** 질문 1개 = 정규화 1개.
→ **20분에 과제 유형을 하나 고른다** ([OPEN_PROBLEM](OPEN_PROBLEM.md) 2번 표: A 배정 / B 원인 / C 보고서 검증 / D 흐름 / E 설계 / F 조기 감지 / G 조회·분석 에이전트). 아래 35분부터는 A 기준 예시다. 다른 유형이면 [ ] 안만 바꿔 읽는다.

**20~35분 · 데이터 확인 질문 (한 번에 묶어서)**
- [담당자] 질문 카드 4~11번 중 애매한 것만, 번호 붙여 한 메시지로.
- "알아서 하세요"가 나오면 바로 🟡로 정하고 다음으로.
- 받은 답마다 "어디에 반영했나"를 한 줄로 남긴다 (Q-ID → config 키·함수). 화면에만 띄우고 계산에 안 넣은 답은 반영이 아니다.

**35~45분 · 부딪히는 것 (비교표 먼저)**
```
[A] 가중치 1·2·3배(또는 1·3·5배)로 각각 결과를 내서 비교표: [선호 지표] | [전체 지표] | [필수 조건 충족] | 비용.
특별한 칸에 특별한 규칙 만들지 마. 후보 전부 썼을 때 상한도 같이.
내 예상: 상한 [필수 조건 전부 충족], [전체 지표] ○% 근처.
```
→ 상한이 0이거나 이상하면: `그건 틀렸다. 상한이 0이면 규칙이 틀린 거다. 되돌려.`
- [담당자] 질문 카드 12·13·14번에 비교표 숫자를 넣어 한 메시지로.
- A가 아니면 비교표만 바꾼다. **B·F:** 원인(신호) 후보를 나란히 — 후보 | 비율 | 전후 차이 | 표본. **C:** 주장 | 다시 계산한 값 | 판정. **G:** 담당자가 실제로 물을 대표 질문 3개 | 필요한 계산 | 답에 쓸 열·출처. 담당자에게는 "이 3개에 답하면 되죠?"로 확인한다.

**45~50분 · CONTRACT 정리**
```
답 원문: [붙여넣기]. interview 원문, decisions 한눈에 갱신.
requirements 맨 위 표(REQ | P | 합격 기준 | D | 확인 방법)로 P0 5개 이상. config.json에 합의값.
"알아서 하세요"였던 건 전부 🟡로 정하고 ❓는 0개로. commit.
```
```
내가 이해한 구조: [읽기] → [변환] → [필수 조건 거르기] → [점수·선택] → [예산·검사]. 틀린 데만 지적해.
```

### 조회·분석 에이전트 과제(G)일 때 — 같은 50분, 할 일은 이렇게

"물어보면 답하는 서비스", "에이전트", 여러 출처(거래·기업정보·기사·보고서)를 잇는 과제면 위 A 예시 대신 이 표를 따른다.

| 분 | 할 일 | 끝나면 남는 것 |
|---|---|---|
| 0~5 | 설치 확인. [담당자] 질문 카드 1·2·3 + "지금 이 판단은 누가, 얼마나 걸려서, 얼마나 자주 하나요?" | 누가 무슨 결정에 쓰는지 한 줄 (D1) |
| 5~20 | [Codex] 데이터 읽기 표 → 막 집계 → 이상 점검 12개. 특히 **1 이름 표기 변형 · 3 거래 방향 · 5 양쪽에 중복 기록 · 2 단위·통화 · 6 기간 기준 · 12 사람이 쓴 문서 재계산** | 이름 통일 규칙 + **안 붙은 목록** · 🟡로 정한 것 · 담당자 확인 질문 |
| 20~35 | [담당자] 한 메시지로: ① "이 3개 질문에 답하면 되죠?"(대표 질문 3개) ② "위험·이상으로 볼 기준은 ○○ 이상으로 할게요, 맞죠?" ③ "답을 보고 실제로 하는 행동이 뭔가요?" ④ 점검에서 나온 확인 질문 | 대표 질문 3개 ✅ · 판단 기준 숫자 · 답 뒤의 행동 |
| 35~45 | [Codex] 대표 질문 3개를 막 집계로 **한 번 직접 답해 본다** (아래 프롬프트). [담당자] "답이 이런 모양이면 되죠?"로 표를 보여 준다 | 질문별 답 초안 표 · 데이터에 없는 것 목록 |
| 45~50 | CONTRACT: P0 REQ 6개 + config.json(판단 기준·기간·상위 N) + 구조 한 줄. ❓ 0개. commit | requirements 표 · commit |

**35~45분 프롬프트**
```
코드 구조 만들지 마. 대표 질문 3개: [질문1] [질문2] [질문3].
질문마다 표로: 필요한 계산 | 쓰는 파일·열 | 지금 막 계산한 답(숫자) | 출처 행 | 데이터에 없어서 못 답하는 부분.
계산은 전부 코드로. 요약 문장에 표에 없는 숫자 쓰지 마.
내 예상: [질문 ○]은 [이름 매칭/기간 기준] 때문에 숫자가 흔들린다.
```

**45~50분 P0 REQ 6개 = 필수 기능** — REQ는 기능 이름이 아니라 **담당자가 하는 동작 + 눈에 보이는 결과**로 쓴다.
1. 담당자가 대표 질문 버튼을 누르면 **결론 한 줄 + 근거 표 + 출처(파일·행)** 가 바로 나온다 (3개 전부).
2. 답의 숫자는 전부 계산 함수 출력과 같다 (AI가 만든 숫자 0개).
3. 데이터에 없는 질문에는 "데이터에 없음: [필요한 자료]"로 답한다.
4. 답 끝에 **누가 · 무엇을 · 끝나면 나오는 것** 조치가 붙는다. 승인은 사람.
5. 정답을 코드로 확인할 수 있는 평가 문항 10개의 정답률이 출력된다.
6. 새 정보 한 줄(조건 변경)을 넣으면 결론·표가 다시 계산되고 **바뀐 것 / 그대로인 것**이 나란히 보인다.

| 보는 사람이 좋아하는 것 | 그걸 만드는 REQ | v0에서 확인하는 법 |
|---|---|---|
| "내일 당장 쓰겠다" — 내 질문에 바로 답 | 1 | 버튼 3개를 눌러 답이 10초 안에 나온다 |
| 숫자를 믿을 수 있다 | 2·5 | 표 숫자 = 함수 출력, 정답률 표시 |
| 모르는 걸 아는 척하지 않는다 | 3 | 데이터에 없는 질문 1개를 일부러 던진다 |
| 그래서 뭘 하라는 건지 보인다 | 4 | 조치에 담당·기한·결과물, 승인 버튼 |
| 상황이 바뀌어도 쓸 수 있다 | 6 | 새 정보 1줄 → 전/후 비교 |

**P1 REQ = P0 6개가 전부 돌아간 뒤(80분~)에만. 위에서부터 하나씩, 하나 끝나면 commit.**

| # | 담당자가 하는 동작 → 보이는 결과 | 합격 기준 | LLM 필요 |
|---|---|---|---|
| P1-1 | 목록에서 대상을 클릭 → 그 대상 중심의 **관계 그림**(직접 연결만, 상위 15개)과 정보 카드 | 그림의 선·숫자 = 표 숫자. 노드 클릭 → 중심이 바뀜 | ✗ |
| P1-2 | 선(거래)을 클릭 → 금액·기간·출처 행 | 출처 행이 원본과 일치 | ✗ |
| P1-3 | **자연어로 질문** → 맞는 계산 함수가 불려 P0와 같은 모양의 답 | 같은 뜻 다른 표현 5개가 같은 함수로 감 · 없는 이름은 후보 제시 | ✓ |
| P1-4 | 답이 만들어진 **단계 패널**: 해석 → 부른 함수 → 결과 → 답, `llm`/`rule` 표시 | 단계마다 입력·출력·걸린 시간 | ✗ |
| P1-5 | "헛경보" 표시 → 다음 답에서 그 대상의 등급이 내려감 | 표시 전/후 결과가 다름, 필수 규칙 알람은 유지 | ✗ |
| P1-6 | 사람이 쓴 문서의 주장 대조 표 · "현재 구현 / 확장 시" 표 | 주장마다 ✅/🟡/❌ + 다시 계산한 값 | ✗ |

- 화면은 3칸: **대상 목록 | 관계 그림 + 정보 카드 | 대화.** 목록·노드·답 속 이름 클릭이 전부 "선택 대상" 하나를 바꾼다.
- LLM은 두 가지만 한다: 질문 → `{함수, 인자}` JSON · 함수 출력 표를 인용한 결론 한 줄. 숫자는 만들지 않는다. 문장에 표에 없는 숫자가 있으면 틀 문장으로 바꾼다.
- LLM 오류·5초 초과·깨진 JSON → 규칙 라우터 → 그래도 안 되면 대표 질문 버튼. API 키는 환경변수로만.
- 그림은 외부 라이브러리를 불러오지 않고 직접 그린다(네트워크가 막혀도 시연되게).

**P1 프롬프트 — 그대로 붙여 넣기 (한 번에 하나)**
```
[P1-1·2] v0 계산 함수는 건드리지 마. 화면을 3칸으로: 대상 목록 | 관계 그림 + 정보 카드 | 대화.
/graph?target=X&depth=1 → {nodes, edges(금액·출처 행)}, 금액 상위 15개만. SVG로 직접 그려.
목록·노드 클릭 → selected 하나로 통일, 세 칸이 같이 바뀌게. 선 클릭 → 금액·기간·출처 행.
내 예상: [대상] 클릭 → 노드 ○개, 가장 굵은 선은 [○○].
```
```
[P1-3·4] src/agent.py 추가. TOOLS = [{name, 설명 한 줄, args}]를 core 함수에서 만들어.
route(question, selected): LLM에 질문+TOOLS → {tool, args} JSON만. 키는 환경변수 [이름], 없으면 바로 규칙 라우터.
JSON 검사: tool이 목록에 있나, 이름은 이름 통일 함수로 매칭, 실패하면 후보 3개.
answer: 함수 출력 표를 주고 결론 한 줄만. 문장 속 숫자가 표에 없으면 틀 문장으로.
오류·5초 초과·JSON 깨짐 → 규칙 라우터. 응답에 route: "llm"|"rule", 단계별 입력·출력·시간(trace).
테스트: 같은 뜻 다른 표현 5개 · 없는 이름 1개 · 데이터에 없는 질문 1개.
내 예상: 5개 중 ○개가 같은 tool로 간다.
```
- LLM이 함수를 잘못 고르거나 없는 숫자를 쓴 순간은 바로 한 줄 기록한다 (무엇을 · 어떻게 알았나 · 고친 commit).
- 140분에 P1 동결. 끝내지 못한 P1은 decisions에 "안 한 것 · 이유 · 다음 할 일" 한 줄.
- P0 6개 중 하나라도 빠진 채 P1을 만들지 않는다. 고민되면 "시연에서 이 동작을 직접 눌러 보일 건가"로 가른다.

```
내가 이해한 구조: [읽기] → [이름·단위 통일] → [계산 함수 3~4개] → [질문을 함수로 잇는 라우터] → [결론 + 표 + 출처 + 조치 답]. 틀린 데만 지적해.
```
- 50분 전 금지: 대화 화면 · 관계 그림 · LLM 연결 · 외부 수집. 전부 v0(80분) 뒤.
- 50~80분은 아래 v0 표의 G 열, 프롬프트는 [OPEN_PROBLEM](OPEN_PROBLEM.md) 2번 G.

**지킬 것:** 숨은 요구는 데이터 보기 전에 · 질문은 2~3번에 묶어서 · CONTRACT 끝에 ❓ 0개 · "내 예상" 3번 · 50분 넘으면 질문 끝, 남은 건 🟡.

**v0 = 제일 단순한 규칙으로 진짜 숫자가 나오는 것.** 화면·엑셀·문서는 v0 다음. 한 규칙에서 10분 넘게 막히면 제일 쉬운 버전으로 🟡 박고 넘어간다.

| 분 | 할 것 |
|---|---|
| 50~60 | 핵심 테스트 3개(단위·방향·필수 조건 1개) |
| 60~70 | 계산 함수 한 파일 + **상한(후보 전부)** 먼저. 상한이 0·100%면 규칙부터 의심 |
| 70~78 | 탐욕 배정(매번 새로 늘어나는 값이 제일 큰 것 하나씩) + API |
| 78~80 | 실행해서 숫자 확인 → 커밋 |

```
지금부터 v0. 20분 안에 끝낸다. 문서 건드리지 마.
src/core.py 한 파일에: 데이터 읽기 → 단위 변환 → [판정 규칙] → 상한(후보 전부) → 탐욕 배정.
규칙은 전부 제일 단순한 버전(칸·행 하나는 대표점 하나, 가중치 1배). 애매하면 멈추지 말고 🟡로 정하고 목록만 줘.
API는 core 결과를 JSON으로 그대로. 화면은 나중.
내 예상: 상한 ○%, v0 결과 ○% 근처.
```

**A가 아닌 유형의 50~80분** — 프롬프트는 [OPEN_PROBLEM](OPEN_PROBLEM.md) 2번의 유형별 v0를 쓴다. 시간 칸은 같다.

| 분 | B·C·F (원인·검증·감지) | G (조회·분석 에이전트) |
|---|---|---|
| 50~60 | 판정·비율 정의 테스트 3개 | 이름 통일 + 안 붙은 목록, 계산 함수 테스트 3개 |
| 60~70 | 후보별 **비율** 표 + 전후 비교 | 계산 함수 3~4개 (LLM 없이, 입력·출력 고정) |
| 70~78 | 튀는 후보 하나만 더 쪼개기 + API | 규칙 라우터 + 답 틀(결론 → 표 → 출처 → 데이터에 없음) |
| 78~80 | 실행 → 숫자 확인 → 커밋 | 평가 문항 10개 정답률 → 커밋 |

**G(조회·분석 에이전트) v0 프롬프트 — 그대로 붙여 넣기**
```
지금부터 v0. 25분 안에 끝낸다. 문서 건드리지 마.
src/core.py 한 파일에: 데이터 읽기 → 이름·단위 통일(안 붙은 목록 출력) → 계산 함수 3개([질문1]·[질문2]·[질문3]용) → answer(질문번호).
answer 출력은 JSON 하나: {결론 한 줄, 근거 표, 출처(파일·행), 조치(누가·무엇·결과물), 모르는 것}. 숫자는 함수 출력 그대로, 문장에 새 숫자 쓰지 마.
데이터로 답이 안 되면 {"데이터에 없음": 필요한 자료}.
규칙은 전부 제일 단순한 버전(기준값 하나, 기간 하나, 상위 N). 애매하면 멈추지 말고 🟡로 정하고 목록만 줘.
LLM 연결·자유 입력·그림 만들지 마. API는 /answer?q=1|2|3 이 JSON 그대로. 화면은 버튼 3개만.
eval.json 10문항(정답을 코드로 확인) 돌려서 맞은 수 출력.
내 예상: 질문1 답은 [○○], 정답률 ○/10, 안 붙는 이름 ○개 근처.
```

v0가 나오면 바로:
```
config의 [판단 기준값]을 ○·○·○으로 바꿔 각각 돌려 비교표: 기준값 | 걸리는 대상 수 | 1위 | 결론이 바뀌나. 내 예상: ○에서 결론이 바뀐다.
그다음 새 정보 한 줄([조건 변경])을 넣고 다시 돌려 전/후 표: 바뀐 것 | 그대로인 것.
```
→ 숫자를 넣어 담당자에게 "기준은 ○로 할게요, 맞죠?" → 🟡를 ✅로.

- **G의 v0 합격선:** 대표 질문 버튼 3개가 전부 답을 낸다(REQ 1·2·4) + "데이터에 없음" 1번 시연(REQ 3) + 정답률 숫자(REQ 5). REQ 6(조건 변경)은 80~100분에 config 값 하나를 바꿔 다시 돌리는 것으로 먼저 만든다.

- v0 화면의 순서는 유형과 상관없이 **결론 한 줄 → 비교표 1개(후보를 나란히) → 오늘 조치 3개(누가·무엇·완료 결과물) → 모르는 것 3줄.** 단서는 맨 아래 한 번만.
- "아니다"를 보였으면 "그럼 무엇이고 지금 무엇을 멈추나"까지 숫자로 간다. 계산해 둔 비교 숫자가 요약에 안 올라가면 없는 것과 같다.
- 큰 설계(그래프 저장소·검색 저장소·여러 에이전트)가 떠올라도 v0는 **함수와 표**로 만든다. 함수마다 `{단계, 입력, 출력, 출처}`를 남겨 단계 패널로 보여 주고, 화면 아래에 "현재 구현 / 확장 시" 2열 표를 둔다. 안 쓴 기술을 쓴 것처럼 적지 않는다. LLM 연결·관계 그림은 80분 뒤.
- **80분에 증거 2개를 남긴다:** 전체 재실행 시간(`time` 출력 그대로) · AI가 틀린 순간 한 줄(무엇을·어떻게 알았나·고친 commit). 아래 "검토자 공격 질문" 표의 재료다.

v0가 나오면 바로:
```
가중치 1·2·3배로 각각 돌려 비교표: [선호 지표] | [전체 지표] | [필수 조건 충족] | 비용. 내 예상: ○배가 꺾이는 지점.
```
→ 숫자를 넣어 담당자에게 "○배로 할게요, 맞죠?" → 🟡를 ✅로.

v0 전 금지: 읽기 모드 15분 넘는 토론 · 문서 칸 채우기 · 화면·엑셀·견적 먼저 · "리스크 말해 줘"류 질문.

## 네 가지를 연결하기

질문/답 **Q-ID** → 선택/이유 **D-ID** → 합격 기준 **REQ-ID** → 실제 명령·결과·근거.
정책 승인 / 구현 검사 / 사용자 결과 수용의 O/X를 따로 쓴다. 파일이 있다는 사실을 승인·실행 성공으로 바꾸지 않는다.

데이터는 **읽기→정규화→정제→판정→순위/집계→표시**로 흐른다. 7 STATE와 별개이고 파일 6개를 강제하지 않는다.
쉬운 말로: **읽고 → 표기 맞추고 → 거르고 → 꼬리표 붙이고 → 순서 정하고 → 보여 준다.** 정규화는 아무것도 빼지 않고 모양만 맞춘다. 정제는 이번 계산에 들어오면 안 되는 행을 뺀다.
- 예 (재고 보충): 파일 읽기 → 단위·품목코드 표기 통일 → 단종·중복 행 제거 → 품목마다 부족/안전 꼬리표 → 부족 큰 순 정렬·발주량 계산 → 화면·엑셀.
- **CONTRACT에서 REQ는 이 6칸으로 묶어 8개 이하로 만든다.** 요청자 답 하나하나는 REQ가 아니라 그 칸 REQ 안의 세부 줄이다. 내가 정한 것(🟡)·P1은 REQ로 만들지 않고 decisions에 한 줄.
- 문제 모양이 다르면 칸 이름만 바꾸고(예: 순서 정하기 → 합계 내기), 해당 없는 칸은 비운다. 그래도 안 맞으면 들어오는 것 → 바뀌는 것 → 나가는 것 3칸.
정상 대표·격리 원본·중복 원본이 배타적일 때만 같은 파일의 원본 레코드 보존식을 쓴다. 경고를 정상 건수에 다시 더하지 않는다.

## 인터뷰 (DISCOVERY)

- 처음 3분은 해법 단어(자동화·AI·화면)를 꺼내지 않는다.
- 순서: 실제 사례 → 지금 우회 방법 → 숫자(빈도·시간·실패 비용) → 누가 쓰고 누가 결정하나 → 경계·예외.
- 성공 기준은 **숫자 + 현재값 + 측정처**로 적는다 (예: 주 반나절 → 10분, 측정: 감사 준비 시간).
- README에 문제가 자세히 적혀 있으면 다시 캐지 말고 갈림길(경계·예외·충돌·결정권자)만 확인하고 빨리 만든다.

## 나중에 설명할 때 (AI 없이 내 말로)

결정은 나중에 다시 설명해야 할 때가 많다. 질문 유형별 틀:
- **왜 이렇게 했나** → 결론 → 근거(Dn·담당자 답·데이터) → 안 했으면 생기는 일.
- **장애가 나면·어디서 틀리나** → ① 약점 지점(파일·함수·데이터·경계값) ② 왜 위험한지·어디까지 번지는지 ③ 다음에 검증·개선할 것.
숫자는 기억나는 것만, 모르면 "확인 못 함"이라고 쓴다. REVIEW·handoff가 설명의 근거다.

### 검토자 공격 질문 5개 — 작업 중에 증거를 모아 둔다
답 틀은 하나: **인정 → 범위 좁히기 → 숫자 출처.** 증거는 끝나고 만들 수 없다. 작업 중에 `fde/work/review.md`의 "방어 증거" 칸에 쌓는다.

| 공격 질문 | 막는 답 | 미리 모을 증거 (없으면 이 답을 쓰지 않는다) |
|---|---|---|
| 데이터 권한·연결 비용은? | 첫 연결 비용은 그대로, **반복 비용**이 줄어든다 | 전체 재실행 명령과 **실측 시간** (`time` 출력 그대로) |
| 실제 라인에서도 맞나? | 보장 못 함. "로직이 돈다" ≠ "효과 있다". 효과는 기존 방식과 나란히 돌려 확인 | 나란히 돌리기 계획: 범위(장비·제품)·기간·성공 기준 숫자 |
| AI가 그럴듯하게 틀리면? | 숫자는 코드가 만들고 AI는 인용만, 확정은 사람 | **AI가 실제로 틀린 사례 ≥1개**: 무엇을 틀렸나 · 어떻게 알았나 · 어디를 고쳤나(commit) |
| 우리도 할 수 있는데 왜? | 능력은 인정, 차이는 **빈도·비용**: 비싸서 드물게 하던 걸 매일 | 담당자에게 들은 지금 방식의 시간·빈도 (Q-ID). 지어낸 숫자 금지 |
| 현장 일만 늘리는 거 아냐? | 사람이 볼 건수를 N → n으로 줄이고, 필수 규칙 알람은 그대로 두고 등급만 나눔 | 하루 검토 건수 전/후 (백테스트면 "백테스트"라고 명시), 사람이 새로 입력해야 하는 칸 수 |

- **담당자 질문 1개는 여기에 쓴다:** "지금 이 판단은 누가, 얼마나 걸려서, 얼마나 자주 하나요?" → 4·5번 답의 숫자 출처.
- AI가 틀린 순간(잘못된 조인·없는 조건 지어냄·숫자 불일치)은 고친 즉시 한 줄 남긴다. 나중에 기억 안 난다.
- 결과물이 사람 일을 늘리면(입력칸·추적 대상 Lot 수십 개) 그 자체가 5번 공격의 근거가 된다. 화면에 새 입력칸을 만들기 전에 "이걸 누가 매일 채우나"를 묻는다.

## 3시간 집중 세션 예시 — 실제 일정이 우선

0~15 입력·질문 / 15~30 합의·검사 계획 / 30~45 최소 실행 / 45~115 P0 / 115~140 사용자 흐름·위험 / 140~155 회귀·설명 / 155~170 fresh run·인계 / 170~180 전달 확인.
80분 구조 동결·140분 새 기능 동결·170분 최종 전달 준비는 참고 경계다. 안전·핵심 오류·확인된 필수 수정은 이유를 남기고 최소 변경·재검증한다. 선택 기능·장식부터 줄인다.
같은 실패 3회면 원인·작은 재현·대안 2개를 확인한다. 긴 작업은 handoff의 다음 3행동으로 재개한다. 전달 규칙·허용 도구·네트워크·승인 절차는 실제 프로젝트를 따른다.

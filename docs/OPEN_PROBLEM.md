# OPEN_PROBLEM — 정답이 하나가 아닌 과제용 카드

QUICKCARD는 "정해진 결과를 정확히 계산·배정하는" 과제에 맞춰져 있다.
과제가 **미션 한 줄 + 핵심 질문 + 평가 기준** 모양이고, 무엇을 풀지부터 내가 정해야 하면 이 카드를 같이 본다.
흐름(묻기 → 정하기 → v0 → 검사 → 전달)과 기록(Q → D → REQ)은 QUICKCARD 그대로 쓴다. 이 카드는 QUICKCARD에 없는 것만 채운다.

1. 문제 좁히기
2. 과제 유형별 v0 (원인 찾기·보고서 검증·신호 정의 등)
3. 조건이 바뀔 때 갱신 절차
4. 결정 카드와 시간 비율
5. AI 지시·통제·검증 서술

---

## 0. 과제 카드 받자마자 (5분)

과제 설명을 아래 6칸으로 **내 말로** 다시 적는다. state.md 맨 위에 둔다.

| 칸 | 적을 것 |
|---|---|
| 미션 | 한 줄 그대로 |
| 핵심 질문 | **원문 그대로 복사.** 최종 결론이 이 질문에 답해야 한다 |
| 배경·사용자 | 누가, 언제, 무엇 때문에 곤란한가 |
| 데이터 | 제공 / 직접 수집 / 없음. **"합성 데이터 제공"이면 일부러 심어 둔 문제가 있다고 가정** |
| 산출물 | 무엇을 보여 줘야 하나 |
| 평가 기준 | 항목 그대로. 배점이 있으면 배점까지 |

바로 이어서 **평가 기준 ↔ 결과물 위치** 표를 만든다. 비는 칸이 생기면 그게 할 일이다.

| 평가 항목 | 결과물에서 보이는 곳 | 근거 파일 |
|---|---|---|
| 문제 정의 | HANDOVER 1~2줄, 화면 맨 위 한 줄 | problem.md |
| 분석·근거 | 화면 표·그래프, 숫자마다 출처 | analysis.md, src/ |
| 검증·신뢰성 | 정규화 기록, 주장 검증표, 테스트 | decisions.md, tests/ |
| 실행 가능성 | 결정 카드, 실행 명령 | HANDOVER, HOW_TO_RUN |
| (그 밖의 항목) | | |

## 1. 문제 좁히기 (5~15분)

넓은 미션을 **하나의 문제 문장**으로 줄인다. 이 문장이 HANDOVER 첫 줄이고, 피칭 첫 문장이다.

```
[누가] 는 [언제·어떤 상황]에서 [무엇 때문에] [무엇을 못 하고 있다].
이번에는 [범위]만 푼다. 뺀 것: [A], [B] (이유: 데이터 없음 / 시간 / 영향 작음).
성공하면 [숫자 지표]가 [현재값] → [목표값]. 측정: [어디서].
```

- 담당자에게 한 번만 확인한다: "**[문제 문장]으로 좁힐게요, 맞죠?**"
- 질문을 못 하는 형식이면 🟡로 정하고, 왜 이렇게 좁혔는지 근거 한 줄을 붙인다.
- 문제를 **다시 정의**하는 게 핵심일 때가 많다. 표면 요청("○○ 만들어 줘") 아래에 진짜 막힌 지점(신뢰·순서·원인·비용)이 있는지 한 번 의심한다.

## 2. 과제 유형 고르기 → 유형별 v0

데이터를 5분 본 뒤 하나를 고른다. 섞여 있으면 **결정에 가장 가까운 것**을 주 유형으로.

| 유형 | 신호 | v0 = 이게 나오면 끝 |
|---|---|---|
| **A. 배정·최적화** | 예산·용량·후보·가중치 | QUICKCARD v0 그대로 (상한 → 탐욕 배정) |
| **B. 원인 찾기** | "요즘 ○○이 늘었다", 이력 로그·변경 기록 | 그룹별 **비율** 표 + 이상 그룹 1개 + 시간축 전후 비교 |
| **C. 보고서 검증** | 사람이 쓴 보고서·요약 + 원본 데이터 | 주장마다 원본 재계산 → ✅ 맞음 / 🟡 일부 / ❌ 다름 표 |
| **D. 흐름·대기** | 시각 기록, 대기열, 처리 순서 | 단계별 대기 시간 분해 + 가장 긴 단계 |
| **E. 설계·제안** | 데이터 없음, "시스템을 설계하라" | 작동하는 최소 흐름 1개 + 가정 표 + 효과 계산식 |
| **F. 신호 정의·조기 감지** | "먼저 감지", "떠오르는", "터지기 전에" | 신호 정의 1개 + 과거 데이터에서 **문제보다 며칠 먼저 켜졌나** |

### F. 신호 정의·조기 감지 v0 프롬프트
```
지금부터 v0. 20분. 문서 건드리지 마.
"문제가 터졌다"의 정의부터 고정: [지표]가 [기준]을 넘은 날 = 사건일.
후보 신호 3개를 계산: [기울기/차이 벌어짐/일부 구간만 증가 등]. 각 신호가 켜진 날을 구해.
표: 신호 | 사건 몇 건을 미리 잡았나 | 평균 며칠 먼저 | 헛경보 몇 건.
내 예상: [신호 ○]이 [○]일 먼저, 헛경보 [○]건.
```
- 신호는 **이미 정점인 것과 지금 오르는 것을 구분**해야 한다: 절대값보다 **변화율·가속·하위 그룹 간 차이**.
- 헛경보 수를 같이 보여 준다. 다 잡지만 매일 울리는 신호는 아무도 안 본다.
- 결론은 "신호 ○가 켜지면 → [누가] [무엇을] 한다"까지 이어야 액션이 된다.

### B. 원인 찾기 v0 프롬프트
```
지금부터 v0. 20분. 문서 건드리지 마.
src/core.py 한 파일: 읽기 → 표기 통일(이름·단위·빈값) → 중복·재측정 제외 → 판정 다시 계산.
그룹 [장비/담당/채널 등]별로 건수가 아니라 비율(실패÷전체)을 내.
시간축을 [변경 이벤트 날짜] 전후로 나눠서 같은 표.
비율이 튀는 그룹 하나만 [하위 구분 A]·[하위 구분 B]로 더 쪼개.
내 예상: [그룹]이 [날짜] 이후 튄다.
```
- **건수 대신 비율**, **전체 대신 전후 비교**, **평균 대신 쪼개기** 세 가지만 지키면 대부분의 함정이 걸린다.
- 원인 후보가 둘 이상이면 하나를 빼고 다시 계산해서 **남는 효과**를 본다 ("A 빼면 B만으로 ○%").
- 표본이 적은 그룹(대략 10건 미만)은 결론 내지 말고 "판단 보류(표본 ○건)"로 쓴다.

### C. 보고서 검증 v0 프롬프트
```
[보고서 파일]의 주장을 한 줄씩 뽑아 표로: 주장 | 필요한 원본 열 | 다시 계산한 값 | 판정(✅/🟡/❌) | 차이 이유.
재계산은 코드로만. 원본으로 재현이 안 되면 "재현 불가"로 쓰고 어떤 정의로 시도했는지 남겨.
내 예상: [주장 ○]이 틀렸다. 이유는 [단위/중복/분모] 같다.
```

### E. 데이터가 없을 때
- 목업 데이터를 만들면 **만든 규칙을 파일로 남긴다** (어디서 가져온 숫자인지, 어떤 가정인지).
- 효과는 숫자 한 개보다 **계산식 + 가정값**으로 쓴다. 가정이 바뀌면 결과가 같이 바뀌게 config.json에.

## 3. 질문을 못 하거나 답이 "알아서"일 때 — 가정 표

decisions의 🟡마다 아래 한 줄을 붙인다. 이게 면접에서 "왜 그렇게 가정했나"의 답이다.

| D-ID | 가정 | 근거 (데이터에서 본 것) | 틀리면 바뀌는 것 (숫자) |
|---|---|---|---|
| D_ | ○○ 값은 ○ 단위로 보고 변환 | 다른 출처와 분포 모양은 같고 크기만 ○배 | 영향 행 ○개, 결론 ○○이 바뀜/안 바뀜 |

"틀리면 바뀌는 것"을 실제로 한 번 돌려 본다. 결론이 안 바뀌면 그렇게 쓴다. 그게 가장 강한 근거다.

## 4. 조건이 바뀔 때 — 갱신 절차 (10~15분)

과제 도중 새 정보·조건이 들어온다고 **처음부터 가정**한다. 그래서 정책 값은 처음부터 config.json에 둔다.

```
1. 새 정보 원문을 interview에 그대로 기록 (시각 포함)
2. 화면·HANDOVER에 "분석 갱신 중" 표시
3. config.json만 바꿔서 재실행 (코드 수정 최소)
4. 전후 비교표: 지표 | 이전 | 이후 | 바뀐 이유
5. 결론이 바뀌었나? → 바뀌었으면 새 D 추가(이전 D는 취소선), 안 바뀌었으면 "검토함, 결론 유지 + 이유"
6. 화면에 "마지막 갱신: 시각 · 반영한 정보" 한 줄
```

프롬프트:
```
새 정보: [원문]. 코드 말고 config.json의 [키]만 바꿔서 다시 돌려.
전후 비교표(지표 | 이전 | 이후)와 결론이 바뀌는지 한 줄. 표본이 적으면 "판단 보류"라고 써.
내 예상: [결론 유지 / ○○로 바뀜].
```

## 5. 결정 카드 — 결과의 마지막 모양

분석 결과를 **사람이 내일 바로 실행할 수 있는 결정**으로 바꾼다. 화면 맨 위와 HANDOVER에 같은 내용.

```
조치: [무엇을] [어디에]          기한: [언제까지]
근거: [핵심 숫자 2개] (출처: 파일·계산 정의)
안 하면: [하루/주당 손실 숫자]
반대 증거·모르는 것: [한 줄]
승인: [결정권자] — 버튼/체크는 사람이 누른다
```

- 결정 카드는 **1순위 하나 + 나머지 2~3개**. 많으면 아무도 안 읽는다.
- "당연하게 해 온 방식"에 대한 제안이 있으면 별도 카드 한 장 (운영 규칙 바꾸기).
- 숫자는 코드가 계산한 값만. 문장 안에 직접 쓴 숫자는 출처를 붙인다.

## 6. 시간 비율 — 총 시간이 다를 때

QUICKCARD 시간표는 180분 기준. 총 시간 T에 비율로 맞춘다.

| 구간 | 비율 | T=150분 | T=180분 | T=330분 |
|---|---|---|---|---|
| 과제 카드·문제 좁히기 | ~8% | 0~12 | 0~15 | 0~25 |
| 데이터 읽기·질문·CONTRACT | ~20% | ~40 | ~50 | ~70 |
| **v0 (숫자 나옴)** | ~45% | **~65** | **~80** | **~110** |
| 검증·쪼개기·결정 카드 | ~75% | ~110 | ~140 | ~230 |
| 새 기능 동결 → 화면 다듬기 | ~88% | ~130 | ~160 | ~290 |
| HANDOVER·실행 확인·전달 | 끝 | 150 | 180 | 330 |

T가 길어도 v0는 **110분을 넘기지 않는다**. 남는 시간은 검증·갱신 대비·설명 준비에 쓴다.

## 7. 설명·질문 대비 — 끝나고 바로 물어보는 것

HANDOVER를 위에서부터 읽으면 답이 되게 만든다. 질문별 답 틀:

| 질문 | 답 틀 |
|---|---|
| 문제를 어떻게 정의했고 왜 그렇게 좁혔나 | 문제 문장 → 뺀 것과 이유 |
| 판단 근거는 | 숫자 2개 + 출처 + 쪼개 본 결과 |
| 이 문제를 겪는 사람·규모는 | 건수·비율·비용으로 (데이터에서 센 값) |
| 일시적인지 추세인지 어떻게 아나 | 시간축 전후 비교, 기간 길이, 표본 수 |
| AI가 틀린 숫자를 내면 | 숫자는 코드가 계산, AI는 인용만. 테스트·재계산 경로 |
| 왜 이 부분은 사람에게 남겼나 | 비용·책임이 큰 결정, 데이터에 없는 맥락 |
| 조건이 바뀌면 | config 변경 → 재실행 → 전후 비교 (4절) |

모르는 건 "확인 못 함"이라고 말한다. 지어내지 않는다.

## 8. AI 지시·통제·검증 서술 — 1페이지 (마지막 15분)

AI를 **어떻게 부리고, 어디서 막고, 결과를 어떻게 확인했는지**를 제출물로 요구하는 경우가 있다. 요구가 없어도 설명 때 쓴다.
새로 쓰지 않는다. decisions의 예측·추적 기록, review의 "AI 제안 거절"·"직접 한 검증", git log에서 옮긴다. `work/ai_control.md`:

```
## 역할 분담
- 사람: 문제 정의, 질문, 정책 값 결정(D), 최종 승인
- AI: 데이터 읽기 표, 코드 초안, 테스트 초안, 문서 초안
- 코드: 모든 숫자 계산 (AI가 직접 계산한 숫자는 쓰지 않음)

## 지시 방식 (대표 프롬프트 3개, 원문)
- [단계] "…"  → 왜 이렇게 지시했나 한 줄

## 통제 (AI를 막은 곳)
- 금지 규칙: [AGENTS 규칙 중 핵심 3개]
- 거절한 AI 제안: [제안] → [거절 이유] (review에서)
- 멈춤 지점: [어디서 사람 확인을 받았나]

## 검증 (AI 결과를 믿은 근거)
- 내 예상 vs 실제: [표에서 2~3줄, 틀린 줄 포함]
- 테스트: [몇 개, 무엇을 막는지]
- 손으로 다시 계산한 것: [한 건, 값 일치 여부]

## AI가 틀렸던 사례
- [무엇을 틀렸나] → [어떻게 알아챘나] → [어떻게 고쳤나]
```

"AI가 틀렸던 사례"가 0개면 검증을 안 한 것처럼 보인다. 작은 것이라도 실제 사례를 쓴다.
